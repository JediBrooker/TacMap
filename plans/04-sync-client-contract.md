Status: binding for the SP2 and SP3 client work on Android and iOS. Scope is the
SP2 and SP3 sections of `plans/03-unit-sync-revision.md`; SP4 items are listed at
the end and are out of scope.

## 0. Ground rules

1. **Wire compatibility.** No frame format changes, no new frame types, no new
   fields, no new headers. Everything here works against the shipped pre-SP1
   relay and the SP1 relay. Nothing assumes a relay capability. Anything that
   needs one is SP4 (section 24).
2. **Security.** `docs/THREAT_MODEL.md`, ADR-001 and ADR-004 stay binding.
   Four rules below relax current ADR or threat-model wording. Each is marked
   **[relaxation]**, carries its security argument here, and ships only together
   with the doc change listed in section 25. Until a doc change lands, the client
   keeps the current behaviour for that rule.
3. **Identical behaviour.** Both platforms implement the same policy units with
   the same names (section 23) and pass the same scenario vectors. Platform
   differences are allowed only where a platform API forces them; each one is
   called out.
4. **Nack and close text is relay data.** Nack codes, close codes and HTTP
   statuses are unauthenticated relay statements. They may only cause the client
   to drop, retry, pause or reconnect its own work. They never change replay
   state, never mark data authentic, and are never reported with the SECURITY
   issue kind (with the one exception in 7.3 where the relay rejects our own
   signed identity).

### 0.1 Vocabulary

- **Join**: the life of one room membership in one manager, from `join` to
  `leave`, join-code change or process death. Survives reconnects, Activity
  pause and backgrounding.
- **Session**: one WebSocket with its session domain `sd`, from open to close.
- **Stable session**: CONNECTED (hello-ack received) and either the first
  `op-ack` of this session has arrived or it has been CONNECTED continuously for
  `backoff.stableSessionMs` (30 s).
- **PAUSED_ACTION_REQUIRED**: socket closed, `wantConnected = false`, room, keys,
  replay state and chat binding kept, a persistent issue shown together with the
  existing **Retry** action (`ui_retry_942087cc`, "Retry" / "Erneut versuchen").
  Retry resets all failure counters and connects. Rows marked
  `retryOnForeground` also retry once on the next foreground return.
- **MUTATIONS_PAUSED**: socket and session stay up for presence, chat and
  inbound apply, but no `put`/`del` is reserved or sent for the rest of the join.
- **Surface once (scope)**: report the issue to `SyncIssueLifecycle` and the
  toast stream at most once per issue key per scope (`join`, `session`,
  `failure chain`, `background period`). A per-join `surfacedKeys` set enforces
  it. The banner semantics of CONNECTION vs SECURITY are unchanged (a SECURITY
  issue stays until dismissed or a later verified clean snapshot).
- **Suppressed until local edit**: per-join map `localId -> journal generation`.
  The diff pass does not publish that object while the local model revision
  journal generation for it is unchanged. A local edit (generation advances)
  releases it.
- **skippedWireIds**: per-join map of wire IDs whose snapshot or live record was
  skipped (section 2), with the category.

## 1. Inbound pipeline and batching (foundation for SP2 and SP3)

Findings: S2-09, S3-10, S4-04, S5-01, S5-03, S3 verifier note 4.

1. Transport callbacks only enqueue. The reader hands each complete frame to a
   bounded FIFO queue (`persistenceBatching.inboundQueueMaxFrames` 1,024 /
   `inboundQueueMaxBytes` 16 MiB) after the size and budget checks of section 12.
   - Android: `SyncInboundCallbackGate` releases the reader when the frame is
     enqueued, not when it is processed. If the queue is full the reader waits
     up to `watchdogs.inboundQueueSpaceTimeoutMs` (60 s), then fails the socket
     as a slow consumer (today's path, new timeout).
   - iOS: the receive loop re-arms only after the frame is enqueued; a full
     queue delays the re-arm (natural backpressure).
2. One serial protocol worker drains the queue in arrival order, in batches of
   at most `inboundBatchMaxFrames` (64) frames that are already queued. A batch
   never waits for more frames. Split before a second `put`/`del` for the same
   wire ID, or before a frame that reads the committed model or sends a response.
   Each resulting subgroup is a logical batch with the write limits below.
   This keeps earlier layer adoption and model effects visible to the next
   mutation for the same object; at worst 64 frames form 64 logical batches.
3. Per batch, in order: validate frames, apply all replay-state changes in
   memory in frame order (later frames in the batch see earlier ones), persist
   **one** replay transaction, apply model changes with **at most one write per
   store**, verify receiver hashes, clear all resolved pending markers in **one**
   replay write, then publish UI state. Nothing from a batch is visible before
   its replay transaction is durable. A persistence failure rolls back the whole
   batch and takes today's fail-closed path.
4. The snapshot is one batch by definition (section 2), whatever its size.
5. Durable ordering inside a batch is unchanged from ADR-001 section 8:
   reservation or acceptance persisted, then model apply, then hash verify,
   then marker clear.

## 2. Snapshot validation: fatal vs skip (poison records)

Findings: S2-10, S3-03, S4-01, S3 verifier note 3, S4 verifier note (iOS
identity collision, tombstone `c` divergence).

### 2.1 Classification

Each snapshot item is classified independently. The lists are
`snapshot.fatalStructural`, `snapshot.skipUnverified`,
`snapshot.skipUnsupported` in the fixture.

| Category | Examples | Effect |
|---|---|---|
| **Fatal structural** | begin when not CONNECTING or a second begin, non-integer seq, page before begin or after the final page, `more` not boolean, `items` not an array, an item that is not an object, an item whose `id` is missing or not canonical 32-byte base64url, duplicate wire ID, end before final page, end seq mismatch, aggregate over 54,525,952 bytes, more than 10,000 items | Whole snapshot rejected, nothing committed (2.4) |
| **Skip, unverified** | bad `vs`, `by` differs from the stamp actor, non-canonical `pub`/`sd`, actor binding mismatch, `pub` differs from the pinned key, `kind` syntax invalid, `t`/`deleted` inconsistent, `ct` not canonical or too short or too long, AEAD open fails, inner JSON invalid, signature missing or invalid, tombstone inner object has any key other than `sig` | Record skipped, counted as unverified |
| **Skip, unsupported** | AEAD and signature verify, but: unknown `kind` (for example `route`), empty or missing content, importer fails, `invalidSkipped != 0`, not exactly one object, kind/content mismatch, embedded UUID does not match the wire ID (including an embedded id that isn't a canonical UUID string, 2.7), iOS identity collision with an object of the other kind, expected model hash unavailable | Record skipped, counted as unsupported |
| **Ignore** | authenticated but does not beat local replay state | unchanged behaviour, not counted |

Notes that make the two platforms identical:

- A record of unknown `kind` is still AEAD-opened and signature-checked with that
  kind in the AAD and preimage, so the client can tell "authentic but newer
  format" (unsupported) from "garbage" (unverified).
- Tombstone inner objects must be exactly `{"sig": ...}` on both platforms
  (iOS already rejects `c`; Android must now reject any extra key). This is a
  tightening; honest v3 senders on both platforms only send `sig`.
- iOS `SyncRemoteModelMutationError.invalidPayload` and `.identityCollision` on
  the snapshot and live paths become skip-unsupported. `.persistence` stays
  fail-closed.

### 2.2 What a skip does and does not do

A skipped record:

- is **not** committed to replay state (no stamp, tombstone, actor pin,
  `localCounter` or content hash change, no pending marker);
- is **not** applied to the model;
- is added to the join's `skippedWireIds` with its category;
- is counted for the notice.

The snapshot still commits with its `seq` (`lastSnapshotSeq = max(old, seq)` as
today), the accepted records are applied, and the hello is sent.

Authentic-but-unsupported records are deliberately **not** committed either. If
they were, a later app version that can parse them would see an "exact persisted
mutation" without a pending marker, never apply the newer content, and push its
own older copy over it. Not committing keeps the upgrade path clean.

### 2.3 Security argument **[relaxation of ADR-001 sections 9 and 10]**

The relay can already omit any record from a snapshot: the snapshot is fenced by
a relay-chosen `seq`, not authenticated as a set. Skipping a record that fails a
per-record check is observably identical to the relay omitting it, provided the
skip has no side effects. It has none: no replay state, no model change, no
counter baseline change (2.2). The authenticated baseline is therefore computed
exactly as if the record were absent, and the advance window is unchanged.
Structural and fence violations stay fatal because they are the cases where
partial acceptance would let the relay choose an ordering (duplicate IDs) or
splice sessions (fence mismatch).

The reaction to a skip must not become a new lever:

- **No republish of stale local copies.** For a local object whose wire ID is in
  `skippedWireIds`, the diff pass publishes it only if the local journal
  generation for that object has advanced since the skip was recorded (the user
  edited it in this join). Without this rule a client that cannot parse a newer
  record would push its older copy over the newer one on every reconnect (benign
  version skew turning into data loss). Under attack this adds nothing: a relay
  could already cause the same push by omitting the record.
- **No reconnect.** A skip never causes a reconnect, a fail-closed stop or a
  `wantConnected = false`.
- **No relay hints.** The outer `vs` of a skipped record is never used, not even
  to pick a higher counter for our own next write.

### 2.4 Structural failure handling (both platforms)

Nothing from the snapshot is committed. Report the existing snapshot
authentication failure message (SECURITY, scope `session`), close the socket
(`localCloseActions.structuralSnapshot`) and reconnect with `transient` backoff
(no reset). After `stopThresholds.structuralSnapshotFailuresBeforeStop` (3)
consecutive structural failures without an intervening hello-ack, enter
PAUSED_ACTION_REQUIRED with `SNAPSHOT_MALFORMED_STOPPED`. This replaces today's
Android behaviour (reconnect forever) and iOS behaviour (`failClosedV3`, stop on
the first one). Retrying is safe because a rejected snapshot commits nothing.

### 2.5 How skips are surfaced

- `SKIPPED_UNVERIFIED` (SECURITY, once per join): "Some synced objects failed
  verification and were ignored (count: {1}) ..." A snapshot with any
  unverified skip is not a verified clean snapshot, so it does not retire older
  SECURITY issues.
- `SKIPPED_UNSUPPORTED` (CONNECTION, once per join): "Some synced objects use a
  format this version of TacMap can't display ... Update TacMap".
- The count is the number of skipped wire IDs in the snapshot that triggered the
  notice. A later identical snapshot after reconnect shows nothing new.

### 2.6 How a skipped ID is kept out of stale-nack loops

1. `stale` is a benign last-writer-wins loss and never reconnects (section 6).
2. The no-republish rule in 2.3 means an untouched local copy is never sent.
3. If the user edits that object, it is published once at a normal reservation;
   if the relay answers `stale` (the unreadable record has a higher stamp), the
   op is resolved and the object is suppressed until the next local edit.
4. The `stale`-on-own-stamp shortcut in section 6 is disabled for wire IDs in
   `skippedWireIds`, so a skip can never be mistaken for confirmation.

Net effect: at most one publish attempt per user edit, zero reconnects.

### 2.7 Amendment 2026-10-05 (3.0.1): the embedded id is canonical before it is hashed

Finding: sync-android-2. Android hashed the importer's raw feature id with a lenient `uuidToBytes`: it stripped dashes, needed 32 characters and ran `Character.digit` per nibble with no validation. So `3f2a...` without dashes, 32 non-hex characters, or a fullwidth digit produced a wire id that matched a crafted outer id. The record validated, then `validRemote` (`UUID.fromString`) refused it and `persistenceFailure()` stopped sync for the whole room on every Android device, on the live path and on every snapshot. iOS was never affected: it parses a `UUID` value first and gets `embedded_uuid_does_not_match_wire_id`.

Rules (both platforms, snapshot and live paths):

- Before the wire id is computed, the single object's embedded id must match `snapshot.embeddedIdPattern` as a whole string: ASCII hex in 8-4-4-4-12 groups, either case, exactly 36 characters, no trimming, no trailing newline. Anything else is skip-unsupported `embedded_uuid_does_not_match_wire_id` (2.1, 2.2): no stop, no `persistenceFailure`, no reconnect; `SKIPPED_UNSUPPORTED` once per join.
- Uppercase and mixed case are canonical on input (RFC 9562), because UUID strings are case-insensitive. iOS already accepts them as a `UUID` value. Android folds the accepted id to lowercase for the local model id, the same fold as the v2 state key, so one object never ends up with two local ids. One exception keeps that true: when a local object already holds the same UUID under another casing, the record resolves to that stored id instead of the lowercase fold (snapshot validation, the live path, the restage and the snapshot-end identity recheck all use the stored id). Android up to 1.2.2 kept a GeoJSON import's raw feature id, iOS 1.0.x exported uppercase, and 3.0.0 Android stored whatever embedded id it received, so such objects exist. Folding past them made a second copy for a peer's record and turned the device's own record into a room-wide tombstone (review of A7, 3.0.1). Outbound v3 embedded ids are the local id as stored: iOS always sends lowercase; Android sends lowercase for everything it created or received in 3.0.1, and the stored uppercase id for those legacy objects. Receivers must therefore accept either case, which the first rule already requires.
- The wire-id hasher refuses non-canonical input (Android `WireIdHasher` / `uuidToBytes` return null, never lenient bytes).
- Invariant: every record the validator accepts also passes the replay commit's own checks (`validRemote` / `remoteSnapshotValid`). A validated record therefore can never end in `persistenceFailure`. `validRemote` can stay as it is, since a canonical id, folded or resolved to a stored canonical id, is a subset of what it accepts; existing replay files keep loading.
- Vectors: `snapshot.embeddedIdCases`, scenario `poison_embedded_id_skipped`. Each row says how to build the hostile record (the outer wire id is the HMAC of `outerWireIdFromBytesHex`, the bytes 3.0.0 Android's lenient hasher produced) and the expected classification on both paths.

**Amendment 2026-10-06 (3.0.2), the received casing is kept** (finding interop-v3-android-fold-duplicates-on-300). The lowercase fold above had a cost the A7 review missed: shipped 3.0.0 and 2.x Android keep a v3 object under its raw embedded id and upsert by exact id. When a 3.0.1 Android device met a legacy uppercase object for the first time (new member, reinstall, new device), it stored it lowercase, its next edit exported the embedded id lowercase under the same wire id, and every 3.0.0/2.x Android holder of the uppercase id added a second copy; a later delete then tombstoned only one of them. From 3.0.2, Android only:

- An accepted canonical embedded id is resolved through its lowercase form (the state key) to the id a local object already has, in any casing (unchanged), and when no local object has that UUID it is stored exactly as received: uppercase, lowercase or mixed. The fallback is never the lowercase fold. That applies to snapshot validation, the live path, the restage and the snapshot-end identity recheck (`rebindLocalIds` keeps the record's id when nothing is stored).
- Resolution goes through the lowercase state key (local kind, case aliases), so one UUID never gets two local objects on this device. The outbound diff's own bookkeeping (`lastContent`, `kindById`, `forcedLocalDiff`, the deliveries' `localId`, `WireIdIndex.forward`) is keyed by the exact local id; the 3.0.3 amendment below keeps it on one id per UUID.
- Outbound v3 embedded ids are still the local id as stored, so an object first met uppercase goes back out uppercase and shipped holders update their own copy. iOS is unchanged (it parses a `UUID` value and always sends lowercase); in rooms with iOS editors the shipped-Android duplicate remains a documented transitional residual, as it was in 3.0.0.
- Objects 3.0.1 already folded to lowercase stay lowercase; there is no migration.
- Vectors: `snapshot.embeddedIdCases` rows now expect `localId` = the embedded id verbatim plus `stateKey` (lowercase), and `snapshot.embeddedIdCasingCases` (Android) gives the stored-twin cases. Findings list of `poison_embedded_id_skipped` gains this finding.

**Amendment 2026-10-07 (3.0.3), a delete the diff hasn't sent keeps its id** (finding R1-V3-STALE-BASELINE). Keeping the received casing let a record land under a second local id when this device had just deleted its copy under the other casing and the diff hadn't sent that delete yet (offline in the foreground, or inside the diff debounce). The old id stayed in the diff's baseline and looked gone, so the diff tombstoned the object room wide at a fresh stamp while this device kept showing the teammate's edit; it only came back at this device's next reconnect. Android only:

- When no stored object has the UUID in any casing, the record resolves to the id the outbound diff still tracks it under (its echo baseline, a forced re-diff or a delivery in flight, the same sources as the diff's gone list) before falling back to the received id. Snapshot validation (from a copy taken at `snapshot-begin`) and the live path both do this; the restage and `rebindLocalIds` keep that id.
- The outcome is then the same as when the casings match: a newer remote put beats a local delete that never went out, no tombstone is sent, and the object stays under the id this device had, so its next edit exports that casing again.
- When the diff tracks nothing for the UUID (a fresh device, an acknowledged delete) the received id is kept as above.
- Pinned by `SyncStoredIdCasingTest` (snapshot after an offline delete, live inside the diff debounce, both casings plus the matching-casing control). No fixture row: the single-record vectors can't express the diff state.

## 3. Snapshot layer-metadata ordering

Finding: S3-08.

Snapshot records are parsed in item order against a **staged layer set**: the
committed local layers plus the `newLayers` adopted from earlier items of the
same snapshot, first one wins (the same rule the apply step uses). Record *i*'s
importer sees layers added by records 0..i-1, so its `newLayers` and expected
model hash describe exactly what the apply step will produce. The pending marker
persisted at commit carries that staged hash, so crash recovery is consistent.

Off-main validation (section 19) captures a fingerprint of the committed layer
set. If the committed layers changed by the time the batch commits (the user
edited a layer meanwhile), expected hashes for records referencing a changed
layer are recomputed on the protocol worker before the pending markers are
written. Live records use the committed layers at validation time, as today.

Vector: `layer_metadata_staged_in_item_order`.

## 4. Live records and the live counter-window resync

Findings: SP1 review, ADR-001 section 9.

1. Live `put`/`del` use the classification in 2.1. A skip adds to
   `skippedWireIds`; the notices follow the same once-per-join rule.
2. An **authenticated** live record (binding, AEAD and signature pass) whose stamp
   beats local state but whose counter exceeds `roomHighWater + ADVANCE_WINDOW`
   triggers a resync: a clean close and an immediate reconnect for a fresh
   snapshot. It is not a failure and does not touch backoff.
3. Rate: at most one resync per `liveWindowResync.cooldownMs` (60 s) and
   `maxPerHour` (6). During the cooldown the frame is dropped as today and one
   pending resync is remembered for the end of the cooldown.
4. `snapshot-begin.highWater` stays an ignored relay hint.

Security: only a genuinely signed frame from a room member can trigger this, and
a relay can always force reconnects by closing sockets. The cooldown bounds the
cost. Vector: `live_window_resync_cooldown`.

## 5. Room reset and rollback

Findings: S3-02, S6-01, ADR-001 sections 10 and 16 (90-day purge).

| Signal | Meaning | Action |
|---|---|---|
| `snapshot-begin.seq < lastSnapshotSeq` | relay rolled back, or the room was purged after `ROOM_PURGE_TTL_MS` (90 days) or wiped by a pre-SP1 relay | `ROOM_RESET_SUSPECTED` (SECURITY, once per join, suggests a new join code). Keep syncing; per-object replay rules already reject older state. `lastSnapshotSeq` stays the maximum. |
| `op-nack counter-window` | proof the relay's high water is below this device's counters | `ROOM_RESET_CHANGES_PAUSED` (CONNECTION, once per join, persistent until leave). Enter MUTATIONS_PAUSED. No reconnect. |

"Stop + surface once" here means: stop the loop and stop the repeated banner.
For a seq regression the client does not stop syncing, because stopping would
let a pure relay hint halt honest recovery after a purge (where re-uploading
helps teammates still on the code) while adding no protection: replay rules are
unchanged and a malicious relay can stop sync anyway. Writes stop only when the
relay has proved it cannot take them (`counter-window`).

Vectors: `seq_regression_surfaced_once_per_join`,
`counter_window_pauses_mutations_once`.

## 6. Op-nack handling

Findings: S6-03, S3-15, S1-01 (client side), S3 verifier note 2, S6-01.

Every non-retryable nack **resolves** the op: it leaves the delivery tracker,
its retry timer is cancelled and it is not added to reconciliation
(`forcedLocalDiff`). This kills today's loop where a rejected op is re-sent with
the same stamp after every reconnect. No nack is ever reported as SECURITY and no
non-retryable nack cancels the socket except the session codes.

| Code (relay retry flag) | Action |
|---|---|
| `stale` (false) | Ordinary LWW loss. Resolve, no reconnect, no issue. If the rejected stamp equals this device's own persisted stamp for that wire ID **and** the wire ID is not in `skippedWireIds`, treat it as confirmed (set the echo baseline to the desired content when the model still matches). Otherwise suppress until local edit. |
| `not-found` (false, reserved) | Same as `stale`. |
| `counter-window` (false) | Resolve, MUTATIONS_PAUSED, `ROOM_RESET_CHANGES_PAUSED` once per join. |
| `quota` (false) | Resolve, suppress until local edit, existing room-full message (CONNECTION, once per session). |
| `invalid` (false) | Resolve, suppress until local edit, existing "rejected a change as invalid" message (CONNECTION, once per session). |
| `storage` (true) | Keep the op; retransmit through the pacer on the ack-timeout schedule (section 11.3); consumes an attempt. |
| `hello-required` (true) | Reconnect, `transient`. |
| `session-mismatch`, `session-replaced` (false) | Reconnect, `transient`; counts as a session conflict (7.4). |
| unknown code | `retry:true` like `storage`, `retry:false` like `invalid`. |

Why confirming on our own stamp is safe: a stamp is reserved once per local
mutation together with its exact content hash, and the relay cannot forge our
signature, so a stored record carrying our stamp is our write. Any newer
authenticated record for that ID would have reached replay state through the
snapshot or live stream; the only exceptions are skipped records, which is why
`skippedWireIds` disables the shortcut. If the shortcut were ever wrong, the room
still converges on the relay's record at the next snapshot.

Vectors: `stale_nack_no_reconnect`, `stale_on_own_persisted_stamp_is_confirmed`,
`counter_window_pauses_mutations_once`.

## 7. Close codes and HTTP upgrade statuses

Finding: S2-11 (also S3-11, S3-13).

### 7.1 Reading the code

- Android: `SyncWebSocketListener.onClosed(code, reason)` already carries the code;
  `SyncManager` must stop discarding it. If the socket never opened, take the
  HTTP status from the Java-WebSocket handshake failure text
  `/Invalid status code received: (\d{3})/`.
- iOS: `task.closeCode` / `closeReason` after a receive failure; if the task never
  opened, `(task.response as? HTTPURLResponse)?.statusCode`.
- A close the client initiated itself is classified by its local reason
  (`localCloseActions`), never by the code the transport echoes.

### 7.2 Tables

Client-initiated closes (`localCloseActions`): receive budget (1008), oversized
(1009), binary (1003), all watchdogs, liveness timeout, ack exhaustion and
structural snapshot failure reconnect with `transient`; live-window resync
reconnects immediately without counting as a failure; leave and lifecycle
transitions do nothing.

### 7.3 Security note

Only 4010 and 4011 are reported as SECURITY: they mean the relay rejected our own
signed identity, which the user must know about. Everything else is availability.

### 7.4 Session conflicts

4015 and `session-replaced`/`session-mismatch` nacks count as session conflicts.
`sessionConflictsBeforeStop` (3) within `sessionConflictWindowMs` (10 min) enters
PAUSED_ACTION_REQUIRED with `SESSION_CONFLICT` (retry on foreground). This stops
two installs sharing one identity from fighting forever.

Vectors: `close_and_status_table`, `session_conflict_stops_after_three`.

## 8. Reconnect backoff

Findings: S2-14, S3 verifier note 2, S3-02, S4-02.

`delayMs = floorMs + random * min(capMs - floorMs, spreadMs * 2^attempt)`, with
`random` uniform in [0, 1], `attempt` starting at 0, incremented after every
scheduled reconnect, capped at 20 and shared by all classes in the join.

| Class | floorMs | spreadMs | capMs |
|---|---|---|---|
| `transient` | 250 | 750 | 30,000 |
| `slow_busy` | 15,000 | 15,000 | 300,000 |
| `slow_rate` | 60,000 | 30,000 | 300,000 |
| `slow_storage` | 30,000 | 30,000 | 300,000 |
| `slow_unknown` | 30,000 | 30,000 | 300,000 |

## 11. Outbound pacer, in-flight window, retransmission, pre-send size

Findings: S2-04, S3-06, S3-07, S5-08, S5-09, S6-07, S6 verifier note 1 and 4,
S1-09, SP1 open issue (insider backlog steering).

### 11.1 Budget

Two token buckets per socket, reset to full on every new socket:

- frames: capacity 30, refill 120 per 10 s;
- bytes: capacity 1 MiB, refill 2 MiB per 10 s.

Any 10 s interval therefore carries at most 150 frames and 3 MiB, which is
exactly `relayLimits.clientPacing`. Counted: every application frame this client
writes (hello, leave, chat-key and its retries, chat, loc, put, del, and every
retransmission). Not counted: WebSocket control frames.

Interactive reserve: mutations and retransmissions may only spend a token while
at least 10 frame tokens and 64 KiB byte tokens would remain. Presence, chat and
control frames can use the reserve.

Priorities: control (hello, leave, chat-key) > presence > chat > retransmission >
new mutation. At most one presence frame waits in the queue; a newer one replaces
it.

After a 4008 close the next session starts with 15 frame tokens and 512 KiB.

### 11.2 In-flight window

At most 32 put/del frames and 1 MiB of them may be written and unacknowledged at
once (one larger frame may go alone when nothing is in flight). Retransmissions
do not add to the count. Worst-case bunching at the relay (a stalled link that
flushes at once) is one window plus the in-flight cap, 150 + 32 + a few
interactive frames, below the relay's 200. In-flight bytes stay far below the
room backlog (8 MiB), which also shrinks the honest burst an insider can target
with backlog shedding.

Everything outbound goes through the pacer, explicitly including the post
hello-ack resend of recoverable deletes, the first-join publish of the whole local
map, imports, and reconciliation after reconnect.

Stamps for one diff pass are reserved in **one** replay write (section 17) before
anything is queued. A queued entry is dropped if a newer reservation for the same
local object supersedes it before it is written.

### 11.3 Retransmission

- The ack timer for a copy starts when that copy's write completes on the
  transport. iOS: the `send` completion handler. Android: the transport's
  outbound queue has drained past that frame's last byte (track a running
  enqueued-bytes position, poll `outQueue` remaining bytes every 250 ms while
  anything is pending-write).
- While a copy is queued but not written, its timer does not run and no further
  copy is ever enqueued.
- Timeout for attempt *n* (1-based) with *k* of our own mutation frames written
  before it and still unacknowledged:
  `min(30,000, (5,000 + 200 * k) * 2^(n-1))` ms.
- At most 3 attempts (the first write plus 2 retransmissions).
- Exhausted: CONNECTION issue (existing "still unconfirmed ... reconnecting"
  text, no longer SECURITY), close the socket, `transient` backoff; the op goes
  to reconciliation.
- A `storage` nack schedules the next attempt on the same rule.
- Acks never trigger a synchronous full diff; they mark the diff dirty and the
  existing 250 ms debounce runs it (section 17).

### 11.4 Pre-send size check

Before reserving a stamp, compute the exact inner JSON with a signature
placeholder of the real length (86 base64url characters), then
`ctChars = 4 * ceil((innerUtf8Bytes + 28) / 3)` (12-byte nonce + 16-byte tag) and
the exact outer frame bytes. If `ctChars > CT_MAX` (700,000) or the frame exceeds
`MAX_FRAME_BYTES`: reserve nothing, send nothing, suppress until local edit and
surface `OBJECT_TOO_LARGE` once per object per join. Each platform measures with
its own JSON encoder.

Vectors: `pacer_bulk_500_small`, `pacer_large_frames_bytes`,
`pacer_interactive_reserve`, `retransmit_starts_at_write`,
`no_retransmit_while_unwritten`, `object_too_large_not_reserved`.

## 13. Lifecycle parity

Findings: S2-01, S2-12.

Unifying rule: **a lifecycle transition ends the socket session if and only if
it locks the mission-data key, engages App Lock, or detaches the mission stores.**
Everything else keeps the session.

- **Android.** `MainActivity.onPause` always locks the DataKey and tears down
  MapScreen, so the session always ends (or enters background presence, section
  21). What changes is membership: for every joined room, v2 and v3, with or
  without location opt-in, `UnitSyncRuntime.onActivityPausing` routes through a
  suspend path (close socket without a signed explicit leave, detach mission
  state) and keeps the same `SyncManager` with its room, derived keys, replay
  state and chat binding. `acquireForeground`/`attachForegroundStores` reconnects
  without user input. The manager is disposed only on explicit leave, join-code
  change or process death. MapScreen disposal during a pause must not dispose a
  joined manager.
- **iOS.** A `.inactive` scene phase is transient when the DataKey stays unlocked
  (device-bound mode) and the App Lock overlay is not shown. During it: keep the
  socket, keep the chat key and pending chats, keep processing inbound frames,
  and do not reconnect on return to `.active`. `syncForegroundReady` and the
  `ContentView` chat lock must follow this rule instead of `scenePhase == .active`.
  In auth-bound mode `RootGate` locks the DataKey on `.inactive`, so the session
  ends exactly as today.
- Foreground return after a session ended always takes a fresh connection and a
  verified snapshot (unchanged).

Security: on both platforms the only material kept across a pause is what iOS
already keeps across background today (derived room keys, signing seed, replay
state object), in memory only, cleared on leave and process death. No mission
store and no DataKey stays available. Doc change D2 states this.

Vectors: `ios_transient_inactive_keeps_session`, `android_pause_keeps_room`.

## 15. Chat replay fences and history size

Findings: S3-04, S4-06, S4-07.

### 15.1 Fence pruning **[relaxation of ADR-004 section 5]**

A fence `(actor, sd, kid)` is **superseded** when the durable replay state has a
session domain for that actor and it differs from `sd` (Android:
`presenceSessions[actor].sessionDomain`; iOS: `sessionDomains[actor]`).
Superseded fences are deleted before a new identity is admitted, when the room's
chat store opens, and on any chat-store write (no extra write just to prune).
The 256 cap then counts only current fences. At the cap with nothing prunable,
the message is rejected as today and `CHAT_REPLAY_FULL` is surfaced once per join.

Security argument: chat is accepted only from the actor's current authenticated
session (`activeSessions` sd and chat key), and a session only becomes current
through `commitActorHello`, which requires a strictly higher epoch for a new `sd`
and the identical `sd` for an equal epoch. Once the durable state records a
different `sd` at a higher epoch, the superseded session can never be reactivated,
so its fence can never be consulted again. The same durable hello floor already
protects presence; pruning adds no new trust. If the replay state itself is lost
(a quarantined file, which is a visible security event at join), both presence
and chat replay protection degrade together, and the message-ID check in
history still rejects re-delivery of any retained message.

Fingerprints: keep at most 16 per fence on write (Android currently keeps 64;
accept up to 64 on load so existing files stay readable). Fewer fingerprints only
turn an old exact retry from DUPLICATE into REPLAY_REJECTED; both are dropped.

### 15.2 History byte cap

Retention order is local acceptance order (unchanged). Before a write, if the
candidate document would exceed 2,097,152 encoded bytes, drop the oldest messages
until it is at most 1,572,864 bytes (hysteresis), then apply the 500-message
count cap; unread IDs follow retention. Fences and fingerprints are bounded by
15.1, so messages always fit.

Vectors: `chat_fence_pruning`, `chat_history_byte_prune`.

## 17. SP3 persistence batching

| Path | Replay writes | Store writes |
|---|---|---|

| peer hellos | the batch's single transaction | |
| live record batch | 1 commit + 1 clear | 1 per store |
| outbound diff pass (any number of objects) | 1 reservation | |

### 17.1 Presence counters **[relaxation of ADR-001 section 8]**

Today every accepted presence frame rewrites and seals the whole replay file
before the peer is shown. New rule:

- Accepting a counter `c` for a session whose last persisted counter is `p`:
  if `c - p >= 16`, persist **all** current counters in one write with
  `presenceFenceExact: false` **before** exposing the peer; otherwise expose
  without writing.
- Flush every 60 s while any in-memory counter differs from the persisted one.
- Clean points (leave, background entry, disposal) write the exact counters with
  `presenceFenceExact: true`. Before accepting the next frame after such a write,
  write `false` again.
- On load with `presenceFenceExact == false`, the effective floor for every
  session is `persisted + 15`. Absent flag (older files) means exact.

Security argument: the invariant ADR-001 needs is "a counter at or below one
already accepted is never accepted again, across crashes". Before a crash the
in-memory counter is exact. Because a write is forced before exposing any counter
16 or more above the persisted one, the last accepted counter is at most
`persisted + 15`, so the post-crash floor rejects every counter that was accepted
before the crash. The cost is that up to 15 genuine positions per peer can be
hidden after a crash. Replay protection is not weakened.

Vector: `presence_fence_stride_and_crash_floor`.

## 18. Wire-ID index

Findings: S5-02, S4-03, S3-10, S4 verifier note 2.

Build `localId <-> wireId` once per room session after keys and stores are
attached, with one reusable HMAC instance. Maintain it from local store mutation

## 19. Off-main snapshot validation and apply

Finding: S3 verifier note 4 (also S2-09, S5-02).

- Per-record work (outer parse, binding, AEAD, signature, importer parse against
  the staged layers, wire-ID check, expected hash) runs on a background worker,
  sequentially in item order. Pages may be validated as they arrive; nothing is
  committed before `snapshot-end`.
- Inputs captured for the worker: room keys, a copy of actor pins, the committed
  layer set fingerprint, the wire-ID index snapshot.
- At commit (protocol worker): recompute expected hashes if the layer
  fingerprint changed (section 3), re-resolve tombstone local IDs against the
  current index, capture journal generations and prior hashes **now** (not at
  validation time), then follow section 1.3.
- Durable writes run on a serial background persistence executor in the same
  order as today; UI state is published on the main thread only after
  durability. If a store's API forces main-thread commits, a single batched
  commit per store per snapshot on main is acceptable.
- The handshake stall watchdog counts validation progress (section 9).

## 20. Presence efficiency

### 20.1 Stationary suppression (S5-10)

Foreground only. A frame is sent when at least 5 s passed since the last sent
frame **and** one of: first frame of the session; presence config change;
distance from the last **sent** fix greater than `max(10 m, current horizontal
accuracy)` (haversine, R = 6,371,008.8 m); course change over 20 degrees while
speed is at least 1.5 m/s; speed change over 1.5 m/s; or 20 s since the last sent
frame (heartbeat, two chances inside the 45 s receiver retention). Background
cadence is unchanged. Old receivers are unaffected (no wire change).

Vectors: `presence_stationary_heartbeat`, `presence_moving_keeps_5s`,
`presence_config_change_sends`.

### 20.2 iOS presence-only redraw (S5-12)

A presence frame may change only presence-layer state. Move `peers` into a
separate observable consumed only by the presence overlay; assign
`onlineMembers` and `chatRecipients` only when the value changed; let
`DrawingsOverlayView` call `setNeedsDisplay` only when its shape fingerprint
changed. Test: a DEBUG draw counter stays at 0 while 60 presence frames arrive on
an idle map with drawings. Android keeps its current separation (StateFlow at
MapScreen scope); add an equivalent recomposition check if a hook exists.

### 20.3 PBKDF2 off the UI thread (S5-13)

`join` sets CONNECTING immediately (existing text) and runs the 210k-iteration
derivation on a background worker (Android `Dispatchers.Default`, iOS a detached
task). The result is applied on the main thread only if the join token is still
current; `leave` or another `join` cancels it. No new string.

## 21. Background presence

Findings: S2-05, S2-06, S2-07, S2-08, S5-07, S6-04, S6-05.

### 21.1 Entry

On entering background presence mode (Android `enterBackgroundPresenceOnly`,
iOS `updateLifecycle(foregroundReady: false, backgroundPresenceEnabled: true)`):

1. cancel every delivery retry timer and move pending ops to reconciliation
   (iOS today keeps retrying and kills the socket about 23 s later; Android
   already does this);
2. release chat secrets (pending chats fail, unchanged);
3. send one bridge presence frame with the background retention using the
   newest fix no older than 120 s (the threat model's two-minute rule), on both
   platforms;
4. switch the heartbeat to the background values;
5. from now on, discarded inbound frames count only against the background
   budget (section 12).

### 21.2 No retries, no lost acknowledgements

While backgrounded: no delivery retries, no "unconfirmed change" errors, no
socket cancel caused by deliveries. Acks and nacks are dropped with all other
inbound frames. No confirmation information is lost: the foreground reconnect's
verified snapshot already tells the client which ops landed (an exact persisted
record becomes the baseline; an absent one is republished at its reserved
stamp). Vector: `background_entry_with_pending_delivery`.

### 21.3 Wake-safe keepalive

- Heartbeat while timers run: ping every 60 s, dead after 30 s without pong or
  frame (Cloudflare closes idle WebSockets after roughly 100 s; this is not a
  published guarantee).
- iOS: continuous background location keeps the process running, so the timer
  works.
- Android: the CPU sleeps between fixes and Doze defers alarms to about 9 minutes,
  so a timer cannot keep the socket up in a quiet room. The keepalive is
  therefore checked at every wake: on each background location callback, hold a
  partial wake lock (at most 20 s); if no pong or frame arrived in the last 75 s,
  ping and wait up to 10 s for the pong before sending; no pong means the socket
  is dead and 21.4 applies. No extra alarms.

### 21.4 Background reconnect **[relaxation of THREAT_MODEL section 7]**

`BG_RECONNECT_ENABLED` ships true only together with doc change D1. Until then
the client pauses (21.5) instead.

- When: at the next presence send opportunity after a detected drop, or when the
  network comes back, at least 60 s apart, at most 3 consecutive failures.
- Epoch: the next unused value of the spare block reserved at the last
  foreground hello (section 14: persisted floor `next + 64` when background
  presence is opted in). No durable write happens in background.
- Session: fresh session domain; the snapshot frames are drained **unparsed**
  (only fence order and byte ceilings are checked; at most 4 MiB, else give up);
  send hello; wait for hello-ack (30 s); then send presence only. Never send
  `chat-key`, `chat`, `put` or `del` on this session.
- Pause (21.5) when no spare is left, after 3 failures, when the snapshot is over
  4 MiB, or when location eligibility is lost.

Security argument: the threat-model rule exists so that nothing durable is
written behind the mission-key lock and no unverified room data is processed in
background. The reconnect keeps both: the epoch was durably reserved in
foreground (the persisted floor already covers every spare, so a crash cannot
cause reuse), the presence counter is per session and in memory, and the snapshot
and all inbound frames are discarded unparsed. It uses only the in-memory room
key and signing seed that the existing background path already retains, never the
mission-data key or stores. A session without a chat key is not a chat recipient,
so no chat can be routed to it. The relay learns the device's address after a
network change, which it would learn anyway on foreground return.

### 21.5 Pause and surface

If background sharing stops for any reason other than the user: Android replaces
the foreground-service notification with a non-ongoing notification
(`sync_background_paused_title` + `sync_background_paused`); both platforms show
`BACKGROUND_PAUSED` with the pause time on the next foreground return.

### 21.6 Chat to a peer that cannot receive (S6-04)

A remote session whose latest accepted presence advertises a retention window
above 45 s is in background presence mode and processes no chat. Selected-unit
sends to it are blocked locally with `CHAT_RECIPIENT_IN_BACKGROUND` instead of
being routed and shown as Routed; the recipient list may show it disabled. Room
sends are unchanged (Routed / Sent to room never claims delivery, ADR-004
section 7). The bridge frame of 21.1 makes the signal appear right after a peer
backgrounds; the gap before it is a documented residual. The real fix (a
chat-key revoke frame) is SP4. Vector: `chat_blocked_to_background_peer`.

Egress-only subscription (the relay not fanning out to a background socket) needs
a relay capability and is SP4.
