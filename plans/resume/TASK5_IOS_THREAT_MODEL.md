## Findings and disposition

1. **Release screenshot inputs could override saved OPSEC choices. Fixed.** `OpsecSettings.init` processed `TACMAP_UITEST_ONLINE` outside `#if DEBUG` and could publish online tiles/lookups as enabled despite saved false values. The prior Task 4 Release binary contains that input and both OFFLINE/NIGHT_MODE overrides. Launch-environment control is required; this is not a demonstrated remote exploit. The minimal repair compile-excludes the entire transient screenshot block in Release. Debug screenshots retain their existing behavior. No persisted preference or fresh-install default changed. A real settings regression checks transient overrides and unchanged saved choices; the rebuilt production Release binary excludes all three inputs. The central reviewer independently accepted the exact source/test diff.
2. **Keychain/API custody was described as an overbroad silicon guarantee. Shared documentation and introductory source comments corrected.** `DataKey.store` supplies the raw 32-byte AES value to a generic-password Keychain item, rather than creating an AES key through a Secure Enclave API. DEVICE requests `AfterFirstUnlockThisDeviceOnly`; AUTH requests `WhenUnlockedThisDeviceOnly` plus `.userPresence`. Those are app-verifiable API requests, not app hardware attestation. The broader statement “SEP only holds P-256 keys” is inappropriate as a universal hardware claim.
3. **Pause/key lifetime wording omitted accepted exceptions. Shared documentation and introductory source comments corrected.** An authorized recorder retains the same raw general DEK value, scoped by software ownership/lifetime, not a cryptographically derived track-only key. iOS releases its `Data?`; it does not guarantee every backing copy is overwritten. In addition, `RootGate` deliberately keeps `ContentView` mounted under the lock overlay, so already-decrypted mission objects and map bitmaps can remain in memory. AUTH drops the general key cache and chat plaintext/ephemeral endpoints; DEVICE may retain its cache as accepted by ADR-002. Opaque UI and Sync processing gates do not imply mission-memory erasure.
4. **Existing iOS MBTiles metadata admission is already bounded.** The Android audit found an unbounded metadata reader; the iOS counterpart uses at most 64 row descriptors and incremental SQLite BLOB-prefix reads. No matching ordinary-metadata production fix is needed. Additional real-SQLite checks exercise exactly 64 accepted/65 rejected rows and an ignored 16 MiB unknown value, plus all 12 independent shared metadata vectors and seven actual storage-class/zoom vectors. These are additional coverage of an existing control, not red evidence for a new iOS repair.

5. **Consumed bake-extension admission could accept truncated hostile metadata. Fixed and independently reviewed.** The coordinator found the lazy accessor's SQL `length(value)` stops at embedded NUL, while selecting the whole value can copy a large suffix and `String(cString:)` accepts a silently truncated valid prefix. Exact duplicate extensions were selected arbitrarily. Actual old-source tests prove a regular map remains admissible but its `PDFBakeReader` improperly accepts a valid 64-character expected-key prefix followed by NUL+1 MiB junk, and duplicate key rows. The authorized repair consumes only the two baked-reader fields, projects at most two scalar row/type descriptors with a bound canonical key and ASCII-case-insensitive lookup, requires uniqueness/text type, then reuses strict bounded UTF-8 BLOB reading. Oversized/NUL/invalid-UTF8/type/duplicate values read as missing. Ordinary map admission is unchanged; unused extensions are not rejected. Both bakers' legitimate generated fields remain covered by affected native tests.

No other actionable iOS production mismatch was established in the reviewed claims below. Remaining limitations and owner decisions are retained explicitly rather than converted into guarantees.

## Explicit limits and follow-up

Physical-device key authentication/cancellation, actual Keychain access classes under screen lock/reboot, backup/restore flags and erasure, OS screenshot/app-switcher timing, GPS/background delivery and parser exploitation were not established by simulator tests. Default Apple trust validation is an API boundary, not certificate pinning or proof against a compromised trust store/OS. [Apple's Keychain data-protection documentation](https://support.apple.com/en-ca/guide/security/secb0694df1a/web) describes platform classes/ACLs; [Apple's URLSession trust guidance](https://developer.apple.com/documentation/Foundation/performing-manual-server-trust-authentication) describes default handling. Neither constitutes TacMap hardware attestation.

Raw-DEK recording least privilege, reliable memory zeroization, stronger future key formats, traffic-analysis metadata, insider behavior, weak join codes, native-parser/resource risks and whole-snapshot rollback remain disclosed limitations/owner follow-up. Task 4 universal≤1px acceptance remains withheld. No owner decision or accepted policy was silently weakened. Shared threat-model/DEBUG_HOOKS/site edits are owned by the central writer; this report does not independently edit them. This agent independently approved the frozen shared custody/lifetime, egress, metadata/lazy-extension, renderer-limit, EN/DE privacy and relay-eligibility amendments against source and generated vectors; central generation/freshness checks are separate.
